# VinylCast PoC – Build Plan for Claude Code

Nov 8, 2026 · @Martin

## Goal

The PoC proves one chain on existing hardware: turntable → own phono preamp → Behringer UFO202 line in → Raspberry Pi 3 → HTTP audio stream → a named Chromecast device or Cast group, playing for one hour without dropouts.

The output is a working Python service with a CLI, measured CPU load and latency, and a codec decision (MP3 vs FLAC). Code quality can be PoC-grade, but module boundaries should carry into revision 1, where a phone web UI and auto-cast get added on top.

## Scope

In scope:

- Audio capture from ALSA (UFO202), plus a test-tone source so everything except capture runs on a dev machine without hardware
- Encoding via an ffmpeg subprocess: MP3 320 kbps as baseline, FLAC as the candidate
- An async HTTP server that fans one encoded stream out to several clients
- Cast discovery (devices and groups), start and stop playback via pychromecast
- A CLI covering all of the above, plus an input level meter
- Metrics logging and a soak-test script that summarises a run
- A systemd unit so the service can run unattended during the soak test

Not in the PoC (do not build): web UI, auto-cast to last device, phono stage, Home Assistant integration, Wi-Fi provisioning, auto-start on needle drop, authentication (LAN-only), enclosure or PCB, licence file (decided at release).

## Hardware and environment

Development happens on a regular machine; the Pi is the runtime target. Every milestone up to M3 must pass without the Pi.

| Item | Choice | Notes |
| --- | --- | --- |
| Board | Raspberry Pi 3 (existing) | Model B or B+ not yet confirmed: B has 2.4 GHz Wi-Fi only |
| OS | Raspberry Pi OS Lite, 64-bit, current release | Flashed with Raspberry Pi Imager, SSH enabled |
| Audio in | Behringer UFO202 | Class-compliant USB audio, 16-bit; no input gain control. Verify supported rates with `arecord --dump-hw-params` |
| Network | Ethernet during the PoC | Wi-Fi only after the soak test passes on Ethernet |
| Runtime | System Python 3 (3.11 or newer), venv + pip | ffmpeg and alsa-utils from apt |
| Dev machine | Linux or macOS | Uses the `tone` source; no ALSA required |
| Cast targets | At least one single device and one Cast group | Same LAN and subnet as the Pi (mDNS discovery) |

The Pi 3 shares a single USB 2.0 bus between the USB ports and Ethernet. Throughput is far below the limit, but this is a known source of audio glitches and is measured in M5 rather than assumed.

## Architecture

The receiver pulls the audio; the Pi never pushes it. `cast.py` only hands the receiver a URL, and from then on the server has to serve that receiver like any other HTTP client.

The audio path runs top to bottom through one encoder and one hub, so adding a second receiver costs a queue, not a second encode.

## Repository layout

One Python package, `src` layout, one module per component so revision 1 can swap the CLI front end for a web UI without touching the audio path.

  deploy/

## Component specifications

ffmpeg does capture and encoding; Python only moves bytes and controls Cast. Do not decode or resample audio in Python.

### source.py

- `alsa`: `-f alsa -sample_rate <rate> -channels 2 -i <device>`. Default device `plughw:CARD=CODEC,DEV=0`; confirm the card name with `arecord -L` on the Pi.
- `tone`: `-re -f lavfi -i sine=frequency=440:sample_rate=<rate>`, upmixed to stereo. Optional beep mode (short tone every N seconds) for latency checks.
- `file`: `-re -stream_loop -1 -i <path>` for repeatable listening tests.

### encoder.py

- Runs one ffmpeg process: source args, then `-c:a libmp3lame -b:a 320k -f mp3 pipe:1` or `-c:a flac -f flac pipe:1`.
- Reads stdout in fixed chunks and hands them to `framing`; reads stderr line by line and logs warnings (xruns, overruns) to metrics.
- If ffmpeg exits or stdout stalls longer than 2 s, restart it with backoff (1, 2, 5, 10 s) and log the event. Clients stay connected across a restart.

### framing.py

A client joining mid-stream must receive a decodable stream.

- MP3: no stream header. Split output on frame boundaries (sync word plus valid header fields, not the sync word alone). Strip any ID3 tag ffmpeg writes.
- FLAC: cache the stream header (`fLaC` marker plus metadata blocks, ending at the block flagged last). Detect frame starts by sync code plus a valid header CRC-8. New clients get the cached header, then frames from the next boundary.
- Pure functions over bytes, fully unit-tested against fixtures. After an encoder restart, the FLAC header is re-captured and must match the old one; if it doesn't, disconnect FLAC clients.

### hub.py

- One producer, N consumers. Each client gets a bounded asyncio queue of whole frames.
- A client whose queue exceeds 10 s of audio is disconnected and logged; it must never block the producer or other clients.
- Keeps no history for late joiners: they start live at the next frame.

### server.py

- aiohttp on a configurable port. `GET` and `HEAD` for `/stream.mp3` and `/stream.flac` (only the active codec answers 200; the other returns 404), and `/health` returning JSON (encoder state, client count, uptime).
- Response: status 200, `Content-Type: audio/mpeg` or `audio/flac`, no `Content-Length`, `Cache-Control: no-cache`. Ignore `Range` headers and answer 200.
- Log every request with method, path, remote address and all headers. The receiver's actual HTTP behaviour is one of the things the PoC is meant to discover.

### cast.py

- Discovery via pychromecast's zeroconf browser. List each target's friendly name, model, cast type (single device or group), host and port.
- `play`: connect to the named target, wait until ready, call `play_media` with the stream URL, content type, `stream_type="LIVE"` and title "VinylCast".
- The stream URL uses the Pi's LAN IP address (auto-detected from the interface on the default route, overridable in config), never `localhost` or a `.local` hostname.
- Register a media status listener and log every player state change (BUFFERING, PLAYING, IDLE with its idle reason) with timestamps.
- `stop`: stop media and quit the app on the target.

### cli.py

| Command | Does |
| --- | --- |
| `devices` | Lists Cast devices and groups |
| `levels` | Runs the source through ffmpeg `astats`, prints peak and RMS in dBFS once per second, flags anything above −1 dBFS |
| `serve` | Encoder + hub + HTTP server, no Cast |
| `cast --to NAME` | Sends the stream URL to a running server's target |
| `stop --to NAME` | Stops playback on the target |
| `run --to NAME` | `serve` and `cast` in one process; the soak-test entry point |

### metrics.py

- Appends JSON lines: events (encoder start, exit, restart, stall; client connect and disconnect with reason; Cast state changes; ffmpeg warnings) and a sample every 5 s (CPU % and RSS for the Python and ffmpeg processes, client count, bytes out).
- On the Pi, also sample `vcgencmd get_throttled` every 60 s and log any non-zero value. Under-voltage and thermal throttling must show up in the data, not be guessed at.

## Configuration

One TOML file (stdlib `tomllib`), every key overridable by a CLI flag. Defaults are starting points, not decisions.

| Key | Default | Notes |
| --- | --- | --- |
| `source` | `alsa` | `alsa`, `tone` or `file` |
| `alsa_device` | `plughw:CARD=CODEC,DEV=0` | Confirm on the Pi with `arecord -L` |
| `sample_rate` | `44100` | 48000 to be tested; must be a rate the UFO202 reports |
| `codec` | `mp3` | `mp3` or `flac` |
| `mp3_bitrate` | `320k` |  |
| `http_port` | `8800` | Binds on all interfaces |
| `advertise_ip` | auto | IP placed in the stream URL sent to the receiver |
| `cast_target` | none | Friendly name of a device or group |
| `client_max_buffer_s` | `10` | Queue limit before a slow client is dropped |
| `metrics_path` | `./metrics.jsonl` | One file per run in soak tests |

## Build order and acceptance criteria

Build strictly in this order. A milestone is done when every check under it passes and the evidence (command plus output) is reported. M0–M3 run on the dev machine; M4–M6 need the Pi.

1. **M0 – Skeleton.** `pyproject.toml`, package layout, config loading, CLI stubs, ruff and pytest set up.
   - `python -m vinylcast --help` lists all six subcommands
   - `ruff check` and `pytest` pass
2. **M1 – Encode and serve.** `source`, `encoder`, `hub`, `server` with the `tone` source and MP3.
   - `vinylcast serve --source tone` plays in `ffplay` and VLC from `http://<ip>:8800/stream.mp3`
   - Two clients play at once; killing one does not interrupt the other
   - A client that stops reading is dropped after `client_max_buffer_s` and logged
   - Killing the ffmpeg process triggers a logged restart; connected clients continue
3. **M2 – Framing.** MP3 and FLAC framing, and FLAC output.
   - Unit tests for header capture and frame detection, using fixtures generated by ffmpeg, including a chunk boundary in the middle of a frame
   - For both codecs: a client that joins 30 s in and records 60 s produces zero errors with `ffmpeg -v error -i <file> -f null -`
4. **M3 – Cast.** `cast.py` and the `devices`, `cast`, `stop` and `run` commands.
   - `devices` lists at least one single device and one group, labelled as such
   - `run --to <device> --source tone` is audible on the device within 10 s; same for a group
   - Cast state changes and every HTTP request from the receiver appear in the metrics log
5. **M4 – On the Pi.** `deploy.sh`, systemd unit, ALSA source, `levels`.
   - `levels` shows live dBFS while a record plays; loudest passages stay below −1 dBFS (otherwise lower the preamp's output level before continuing)
   - `run --to <device>` plays vinyl on the target via Ethernet
6. **M5 – Soak test.** Metrics complete and `soak_summary.py` done.
   - 60 min run with MP3 to one device: zero encoder restarts, zero client drops, zero BUFFERING events after the first PLAYING, no non-zero `get_throttled`
   - Summary prints average and max CPU per process, event counts and startup latency
7. **M6 – Codec decision.** Repeat M5 with FLAC, then both codecs with a group.
   - Results table in `README.md`: codec × target × pass/fail × CPU × startup latency × notes
   - Decision recorded: FLAC if it passes on every target type, otherwise MP3 for revision 1

## Testing and measurement

The receiver gives no direct dropout signal, so the soak test relies on proxy signals in the log, plus listening.

| What | How it is measured |
| --- | --- |
| Dropouts | Encoder stalls and restarts, ffmpeg xrun warnings, client disconnects, Cast BUFFERING events after the first PLAYING; plus a listener noting audible gaps with timestamps |
| CPU and memory | psutil sample every 5 s for the Python and ffmpeg processes |
| Pi health | `vcgencmd get_throttled` every 60 s |
| Startup latency | Time from `play_media` sent to first PLAYING state, logged by `cast.py` |
| End-to-end latency | Manual: lift the needle, time until silence at the speaker with a phone stopwatch; average of 5 tries. ±0.5 s is precise enough |

Unit tests cover `framing`, `hub` backpressure and `config`. Integration tests use the `tone` source and ffmpeg decode checks, so they run in CI without hardware or Cast devices. Nothing that needs a Cast device runs automatically.

## Risks and open decisions

The biggest unknown is how Cast receivers handle an endless live FLAC stream; the plan is built so MP3 is always a working fallback.

| Risk | Why it matters | Resolved by |
| --- | --- | --- |
| Live FLAC over HTTP not handled by every receiver | FLAC is listed as supported, but an endless stream with no length is a different case | M6 on each target type |
| Unknown receiver HTTP behaviour (HEAD, Range, reconnects) | Server may answer in a way the receiver rejects | Request logging in M3 |
| Groups behave differently from single devices | The group leader fetches the stream and redistributes it | M3 and M6 both test a group |
| Pi 3 shared USB/Ethernet bus | Possible audio xruns under network load | M5 soak on Ethernet |
| Power supply | Pi 3 plus USB audio is prone to under-voltage | `get_throttled` logging |
| UFO202 has no input gain, 16-bit only | Clipping or a weak signal can only be fixed at the preamp | `levels` in M4 |
| Receiver cannot resolve `.local` hostnames | Stream URL fails silently | Always advertise the IP |
| pychromecast API changes between versions | Code written from memory may not match | Claude Code checks the installed version's source |

Open decisions: Pi 3 model (B or B+), 44.1 vs 48 kHz, final codec. None of these block M0–M3.

## Instructions for Claude Code

Paste this section (or the whole plan, exported as Markdown) into the repo as `PLAN.md` and start Claude Code with: "Read PLAN.md and build M0."

1. Read this whole plan before writing code. In M0, write a `CLAUDE.md` with the conventions below and a short summary of the architecture.
2. Build one milestone at a time. Stop after each, run its checks, report the commands and output, and wait for approval before starting the next.
3. Python 3.11+, asyncio throughout, type hints, ruff for linting and formatting, pytest. Runtime dependencies: aiohttp, pychromecast, psutil. Ask before adding any other dependency.
4. Don't write library calls from memory. For pychromecast and aiohttp, check the installed version's source or docs and pin the versions you verified in `pyproject.toml`.
5. Audio processing stays in ffmpeg. Python never decodes, resamples or mixes audio.
6. Anything needing the Pi, the UFO202 or a Cast device: if you're not running on that hardware, write the exact commands for Martin to run, and ask for the output instead of assuming the result.
7. Don't build anything listed under "Not in the PoC". If a milestone seems to need it, stop and ask.
8. One commit per milestone, with the acceptance evidence in the commit message body.
